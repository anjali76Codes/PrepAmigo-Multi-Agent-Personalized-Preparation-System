# Study Materials Generation Pipeline

This document explains how the **Assessment Agent** and **Flashcard Agent** work in the PrepAmigo system, including their generation logic, JSON parsing robustness, database architecture, and evaluation pipeline.

## 1. Overview
When a `StudyPlan` is generated by the Planner Agent, it is grouped into structured 7-day **Sprints**. To prevent overwhelming the user with daily quizzes and flashcards, the generation pipeline intelligently **chunks the days**.

## 2. Sprint Chunking Logic (Levels & Quizzes)
Rather than generating 1 Assessment and 1 Flashcard set per day, the agents compress the learning objectives dynamically across the 7-day sprint based on the Level (L) and Quiz (Q) architecture:
- **L1 & L2 (Days 1-3)**: Level 1 contains 1 topic, and Level 2 contains 2 topics. After Level 2 is completed, the system generates **Q1** (Quiz 1). Q1 covers all topics from L1 and L2.
- **L3 & L4 (Days 4-7)**: Level 3 contains 2 topics, and Level 4 contains 2 topics. After Level 4 is completed, the system generates **Q2** (Quiz 2). Q2 covers all topics from L3 and L4.

**Output for each Q (Q1 & Q2)**: The LLM generates exactly **1 Assessment (10 questions)** and **1 Flashcard Set (5 cards)** to comprehensively cover that specific block of topics.

## 3. Robust LLM JSON Generation
Since the pipeline relies heavily on the LLM outputting perfectly formatted JSON arrays, several safeguards are built into the Assessment and Flashcard agents:
- **Auto-Cleanup**: The agents intercept the raw LLM string and automatically clean up common hallucinated formatting errors (such as trailing commas `,]` and `,}`).
- **Retry Loop**: The LLM invocation and JSON parser are wrapped in a 3-attempt retry loop. If the model generates unparseable JSON or control characters, the agent catches the `JSONDecodeError`, logs a warning, and automatically retries the prompt.

## 4. Database Architecture (MongoDB)
The generated data is directly inserted into the MongoDB cluster, maintaining strict relational links for easy frontend querying.

### Assessment & Flashcard Schemas
Instead of holding a single `sprint_day_id`, these models store:
- `sprint_id`: Reference to the parent Sprint.
- `covered_sprint_days`: An array `[ObjectId]` containing the IDs of all the days the document covers (either 3 or 4 days).

### SprintDay Linking
Once an Assessment and Flashcard set is inserted, the pipeline performs an update on all `SprintDay` documents in that chunk, setting their `assessment_id` and `flashcard_id` fields.

**Frontend Benefit**: When the frontend requests any single Sprint Day, it can use Mongoose's `.populate("assessment_id")` and `.populate("flashcard_id")` to instantly load the full chunk's quiz and flashcards without any extra database queries.

## 5. LLM-as-a-Judge Evaluation Pipeline
To ensure the LLM generates high-quality, relevant materials without hallucinating, an automated evaluation script is included. 

### `evaluate_generation.py`
This script acts as a strict Educational AI Evaluator. It pulls the generated Assessments and Flashcards from the database, compares them against the original `SprintDay` objectives, and generates a detailed Markdown report (`evaluation_report.md`).

**What it evaluates:**
1. **Coverage Analysis (0-100%)**: Did the generated questions actually test all the requested objectives?
2. **Relevance Analysis (0-100%)**: Did the LLM stick to the topic, or did it hallucinate out-of-scope concepts?
3. **Quality Analysis (0-100%)**: Are the questions intellectually stimulating and requiring critical thought?

### Running the Evaluation
To evaluate the latest generation in your database:
```bash
python src/scripts/evaluate_generation.py
```
This will produce a highly detailed `evaluation_report.md` file in the root directory, which can be showcased to demonstrate the system's focus on AI accuracy, quality control, and hallucination mitigation.
